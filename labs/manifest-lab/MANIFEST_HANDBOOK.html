Architectural Dossier: Scaling Supply Chain Security to 100k+ TPS

1. The Problem: The Invisible Supply Chain

Legacy Handling

Enterprises currently rely on Post-Mortem Scans. Once a vulnerability like Log4Shell is public, teams spend weeks manually searching fragments of their cloud infrastructure to see if they are exposed.

The Graph Complexity

Modern apps are graphs, not lists. Ingesting one SBOM/AIBOM involves 5,000+ transitive dependencies. Multiplying this by 10,000 cloud builds a day creates a Data Velocity problem that standard relational databases cannot solve.

Staff Insight: We treat SBOMs and AIBOMs as Forensic Evidence. Per CHFI principles, we prioritize Acquisition without modification. Our Bronze layer is an immutable record of exactly what was submitted by the vendor—including Model Weights and Dataset Metadata—ensuring Non-Repudiation in the event of a supply chain breach or model poisoning incident.

2. The Value Proposition

Manifest moves security from an External Audit to an Internal Capability.

  • Continuous Compliance: Automated OPA policies reject insecure components in the CI/CD pipeline, not after deployment.
  • Proactive Alerting: We notify the client the second a new CVE hits the global database if we detect a match in their stored inventory.
  • Operational Resilience: Handles 100k TPS spikes (Log4j events) while maintaining sub-second serving latency.

3. Architecture & High-Scale Strategy

[CVE FEEDS] → [INGRESS] → [BUFFER] → [BRONZE] → [SILVER] → [GOLD] → [NOTIFIER]

Slice 0: CVE Ingestor (The Pulse)

Queries NVD API v2 and OSV.dev every 60 seconds. New vulnerabilities are treated as Streaming Events, not static files, ensuring sub-5-minute Mean Time to Detection (MTTD).

Slice 1: Multi-Tenant Ingress (Go)

Designed for **1M TPS potential**. Performs lightweight schema validation (CycloneDX 1.6) and deterministic hashing (SHA-256). Uses **Circuit Breakers** to prevent cascading failures.

Slice 2: Burst Buffer (Redpanda)

A C++ Kafka alternative that provides low-latency persistence for incoming wire bytes. Ensures **Zero Data Loss** even during massive ingestion spikes.

Slice 3: Bronze (Forensic S3)

The **Immutable Record**. We use Content-Addressable Storage (CAS). Every SBOM/AIBOM is stored as an exact byte-for-byte copy of the submission for legal audit.

Slice 4: Silver (Vectorized Enrichment)

We use **Polars/DuckDB** to transform raw payloads into enriched Parquet. Vectorized compute on high-mem cloud nodes eliminates the network shuffle costs of Spark.

Slice 5: Gold (Analytical Serving)

**TiDB / Snowflake**. Powers the serving layer with horizontal scale. Separates high-speed serving state from durable analytical state (DDIA Principle).

Staff Architectural Insight: Serving Layer Persistence

Is Redis "persistent" enough? No. Redis is a **Write-Through Cache** for OPA verdicts (10ms latency). Long-term persistence resides in TiDB. Because our Gold layer is Derived Data, we can re-hydrate the entire serving layer from the Bronze "Evidence" in S3 at any time.

4. Proactive Vulnerability Alerting

The Detection Loop

We implement a Reverse Lookup Engine. When a new CVE is published, we join it against the global Gold Layer Inventory. We find the match before the client even knows they are vulnerable.

The Notification Dispatcher

A Fan-Out Switchboard that decouples detection from delivery. If a client's webhook is down, the Dispatcher uses Exponential Backoff without blocking other alerts.

Staff Architectural Insight: The Dispatcher Pattern

To support Email (SES), SMS (Twilio), and Webhooks concurrently, we use a Queue-Based Dispatcher. Every notification is logged for **Forensic Non-Repudiation**, proving the client was warned at a specific timestamp.

5. Machine Learning Integration

Stage 1: Ingestion Anomaly Detection

Detect "Malicious SBOMs"—payloads designed to trigger logic bombs or ReDoS attacks during the enrichment join.

Stage 2: Semantic Security Discovery (RAG)

**Weaviate + Ollama** allows security teams to perform natural language audits: "Find all models trained on copyrighted datasets."

Stage 3: Predictive Vulnerability Scoring

ML models analyze AIBOM dataset hashes to predict model risk even before a CVE is formally assigned by NVD.

6. Disaster Recovery & Observability

Disaster Recovery: We utilize **Kafka Offset Replay**. If the Silver layer crashes, we rewind the consumer. Our Bronze layer is Multi-Region S3, ensuring "Evidence" is never lost if a datacenter goes dark.

Observability (The LGTM Stack): We use Loki, Grafana, Tempo, and Mimir. At 100k TPS, we monitor Saturation and Error Rates via Tracing to follow an SBOM from the Boeing CLI to OPA.

7. Governance & Lineage

We implement **Forensic Lineage** using OpenMetadata:

  • Upstream: Track which vendor CID (Content ID) supplied a specific package.
  • Downstream: Identify every container or AI model currently running a vulnerable component.
  • Data Contracts: Automated checks ensure incoming SBOMs meet CycloneDX 1.6 standards before hitting the processing queue.

  • The Serving API (FastAPI): Interfaces with OPA and Redis to provide sub-second "Allow/Reject" verdicts for CI/CD pipelines.

Step 3: Simulate a 50k TPS Spike

We exercise the Resiliency Layer. The load generator fires a burst of requests to the Go Ingestor. You will observe the Go worker pool managing the load while Redpanda absorbs the write-velocity, ensuring the processing layer never feels the pressure of the spike.

Step 4: Analytical Enrichment (DuckDB + Weaviate)

Step 5: Semantic Security Discovery (RAG)

We transition from keyword search to Intent-Based Discovery. The RAG agent uses Ollama to generate embeddings and Weaviate to find "similar" threats across the entire global inventory.

The "Proof of Work." We follow a specific Content-ID (CID) from the raw evidence in Bronze, through the vectorized transformation in Silver, to the final security verdict in the Gold Serving layer.

Final Staff Highlights

Question Staff Answer
Polars vs Spark? We prioritize Vectorized Execution. For SBOM joins at Manifest's velocity, Spark's network shuffle is a bottleneck. We scale up vertically with Polars/DuckDB to maximize throughput, only scaling out if the graph exceeds multi-terabyte limits.
Why AIBOM? Modern software is Model-Driven. We track model weight provenance as forensic artifacts to prevent adversarial "Model Poisoning" attacks.
Idempotency? We use Content-Addressable Storage (CAS). The SHA-256 hash IS the identity. This ensures redundant CI/CD submissions never double-count risk or storage.
Proactive vs Reactive? Most platforms wait for a scan. We use a Reverse Lookup Engine to notify the client the moment a threat is published to NVD, reducing MTTD to minutes.
